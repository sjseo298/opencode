## 3. Sync procedure

The mechanical flow is already automated — **do not re-invent it**:

1. **Preconditions**
   - Clean working tree: `git status` (commit or stash local changes — note `build.sh` stashes automatically in full mode).
   - `git fetch origin && git fetch upstream`.
   - Optional: `bash scripts/update-sync-guide.sh --check` to see how far upstream has moved.
2. **Run the sync** — `./build.sh` (default = full sync):
   - `git merge origin/dev` → then `git merge upstream/dev`.
   - On conflict it invokes `scripts/resolve-conflicts.py --auto --compile` (LLM resolution + compile verification).
   - Manual equivalent if you prefer to drive it yourself:
     `git merge origin/dev --no-edit && git merge upstream/dev --no-edit`.
   - `--skip-sync` / `--skip-install` modes are available when you only need the build.
3. **Resolve remaining conflicts** against §4 (per-file strategy), then `git add` and complete the merge commit.
4. **Post-merge verification (mandatory)**
   - `bun install`
   - `bun run generate` from `packages/client` whenever the public `HttpApi` changed (never hand-edit generated client files).
   - `bun run check` from the repo root; run affected package tests (e.g. `bun test` in `packages/core`, `packages/tui`, `packages/opencode`).
   - Smoke: `./build.sh --skip-sync` produces a runnable binary.
5. **Push** — `git push origin dev`.
6. **Refresh this guide** — `bash scripts/update-sync-guide.sh` (regenerates the snapshot + appends the sync-log entry), and review §4.1 below.

## 6. Keeping this guide up to date

This index is only as good as its freshness. Rules:

1. **New fork feature/area** (new builtin plugin, new tool, new route group,
   new script): add an area entry (or extend an existing one) in §2 — files,
   anchor commit(s), risk classification — in the **same commit** as the feature.
2. **Fork starts modifying an upstream-owned file:** move that file from the
   §2 area into the §4.2 watch list (or §4.1 if upstream also changed it).
3. **After every sync** (`build.sh` or manual merge of `upstream/dev`):
   - run `bash scripts/update-sync-guide.sh` — it regenerates the §1 snapshot
     and appends a §5 log entry;
   - re-run the §4.1 command and update the guaranteed-conflict table;
   - commit the guide changes with the sync merge or in a follow-up commit.
4. **After a sync where upstream deleted/renamed a path the fork uses**
   (see A4 for the historical case): record it as a finding in §2 of the
   affected area so the next sync is not surprised.
5. Never edit between `SYNC-GUIDE:SNAPSHOT` / `SYNC-GUIDE:CHANGELOG` markers —
   that content is machine-generated.
